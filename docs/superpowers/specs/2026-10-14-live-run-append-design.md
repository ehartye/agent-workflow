# Add workers to an active workflow run

Status: proposed for owner review. Native feasibility was checked against pinned Codex0.162.1, commit `092d3acd6bec3e3a14bdc7e7a2810ab628ab759d`. This document is a design, not implemented or published behavior.

## Outcome and native boundary

The coordinator can add a bounded batch of independent workers to an active run. They share its run ID, generation, concurrency, lifetime-attempt budget, original runtime, access/capability ceiling and recorded input mode. The graph, status, activity, usage and captures show actual added workers. Existing work continues. No model is asked to rewrite the original workflow script.

Native `thread/start` followed by `turn/start` can execute another worker. Exact active-turn steering already uses `turn/steer.expectedTurnId`. Native `turn/start` may steer a busy thread and must not be used to allocate a separate task. The pinned request union has no `workflow/append` or `worker/create` method: durable admission belongs in our engine, using the existing native backend.

## Approaches considered

| Approach | Time | Risk | Complexity | Best practice | Maintainability |
| --- | --- | --- | --- | --- | --- |
| **Live independent append (recommended)** | Requires admission/replay/race implementation and tests; accepted work need not wait for the original script to finish. | Replay corruption, duplicate dispatch or completion races have serious consequences; transactional identities and fail-closed recovery are mandatory. | Adds one durable inbox and separates script order from physical worker slots. | Reuses the owned scheduler/native backend and records every effect. | One execution path; versioned receipts and explicit recovery rules. |
| Existing edited-script resume | Available now, but waits for settlement and creates a new generation. | Lower implementation risk; replay still needs verified unchanged work and source-awareness. | No new subsystem. | Correct existing recovery mechanism, but does not meet live addition. | Existing supported behavior remains useful and unchanged. |

## Public surface and scope

Add an authenticated CLI `append RUN --session SESSION --generation N --request-id UUID --tasks-file FILE`, plus a read-only receipt inspection surface. `tasks-file` is a regular strict UTF-8 JSON file of at most512KiB; its normalized payload is separately limited to512KiB. It contains exactly `{tasks:[{id,prompt,options}]}`, at most32 independent tasks with unique nonempty IDs of at most200 characters and prompts of at most65536 UTF-16 units each. The options subset is `label`, `phase`, `skills`, `requireTools`, `timeoutMs` and `schema`, validated by existing agent rules; appended tasks use one attempt and the run's original model/workspace defaults. They cannot supply `dependsOn`, permissions, arbitrary plugin roots, executable grants, installs, scripts or retry settings. Existing stricter per-record, lifetime and input limits still apply.

The initial slice is CLI plus existing status/watch/dashboard projections. It does not add a dashboard authoring form, dynamic dependency editing, live skill grants, a second runtime or a planner service. Appended results are explicit worker results; the original guest `state.result` is preserved and never represented as having consumed later work. Public documentation must distinguish the new candidate from installed0.3.5 and reject unsupported retained runtimes clearly.

## Durable admission and execution

The originating-session request includes exact generation and a caller-generated request ID. A transaction validates that the run is accepting additions, checks immutable identities and remaining lifetime capacity, allocates contiguous physical worker slots, records normalized task hashes and a receipt, then acknowledges. Same request ID and same payload returns its existing receipt; conflicting reuse rejects. A lost response is inspected by request ID, not blindly repeated under a new identity.

The controller alone dispatches admitted tasks through its existing scheduler and `backend.execute`. They use genuine selected skills/tools from the run's original bundle and inherit its workspace mode. For a run whose default is an isolated writer, admission requires the original verified captured inputs; an absent, unfinished or invalid snapshot rejects the append rather than silently capturing newer source. Default parent-access readers currently use the live launch directory: they keep that behavior, explicitly recorded as `originalLiveDirectory`, rather than falsely claiming frozen content. That task scope is not a filesystem sandbox. A receipt names `originalCapturedInputs` plus its manifest hash when that mode actually exists. Sharing a run does not copy predecessor edits or widen parent authority. Run-wide concurrency and attempt budgets include both guest and appended calls.

Script invocation ordinal is separate from physical worker position. The guest's ordered hash chain contains only guest calls, while appended tasks have request-bound identities. Replay uses these identities rather than assuming that every physical position corresponds to the next guest call. Interleaved additions cannot invalidate an unchanged completed writer or masquerade as a guest result.

Each origin is explicit: guest invocation ordinal, or originating generation/request ID/task ID for an addition. Guest dependency hashes resolve to stable origins rather than transient physical positions. Cached copies retain both source generation and source position for earlier activity/patch reads. Current-generation worker positions remain contiguous. Normal replay can reuse verified completed appended workers with the same identities and original source/backend/capability fingerprints. Noncompleted additions require explicit effect reconciliation/restart; normal resume refuses them with an actionable error rather than silently submitting them again.

Restart retains the existing physical-suffix meaning. The preview freezes the affected old-generation origin identities, including interleaved appended workers; it never narrows the suffix to only the selected task. The coordinator reviews that complete affected set and its effects before admission. The new generation maps those origins to current contiguous slots and marks reused source positions explicitly. Changed guest calls invalidate their guest-chain suffix; independent completed additions remain reusable only when outside the explicitly approved restart set. Test guest A, appended X, then guest B depending on A across both ordinary resume and suffix restart.

At normal completion, one transaction closes addition admission only after the guest finishes and all accepted work settles. An append racing this closure has exactly one winner: durably accepted and drained, or explicitly rejected before dispatch. Pause closes admission while allowing work to settle; Stop closes admission, interrupts owned active turns and preserves queued/uncertain outcomes. A crash after dispatch intent cannot automatically resubmit an uncertain native effect. Existing strict owned cleanup, unknown-state blocking and capture integrity remain mandatory.

## Transaction, budget and receipt ownership

Use one authoritative generation-scoped admission ledger for accepting/closed state, next physical slot, consumed attempts and reserved attempts. Guest admission/retries and appended batches acquire capacity through the same transaction helper. External append requests write only inbox/task/receipt records and this ledger; they never update counters inside the controller's stale in-memory header. Header projections derive counters from authoritative storage. Pause, Stop, normal completion and admission closure use the same generation/revision comparison, so later header writes cannot reopen admission or erase a reservation.

An accepted appended task reserves one attempt. Moving from queued to dispatch-intent atomically consumes that reservation before native submission. Consumed attempts never decrement. Cancellation can release a reservation only with affirmative evidence that dispatch-intent was never entered. Concurrent batches and guest retries cannot each spend the same remaining capacity. Process loss after intent leaves an uncertain task unknown and blocks automatic resubmission; admitted-but-undispatched tasks remain identifiable and need an explicit verified recovery decision.

Request IDs are scoped to run ID and originating generation. Hash the normalized task payload together with original runtime, access, capability and input-mode identities. The receipt includes those identities, request ID, payload hash, accepted task IDs/positions, timestamps and per-task states. Receipt states are `queued`, `active`, `settled`, `rejected` or `unknown`; these describe admission/delivery, not a new worker execution-status vocabulary. `settled` preserves each actual completed/failed/cancelled outcome. Read by `append-receipt RUN --generation N --request-id UUID`; filesystem read access is sufficient for CLI inspection, while HTTP inspection retains dashboard authentication. A conflicting request ID rejects without executing anything. Unsupported retained runtimes reject append before mutating their records; no old JSON reinterpretation or runtime migration follows.

An appended execution/schema/readiness failure makes the aggregate run failed while preserving the guest's original result. Independent healthy work continues unless an existing fatal isolation/cleanup condition closes the whole run. Unknown effects use the existing failed aggregate status, retain unknown worker/receipt evidence and keep existing replay blocks; this design adds no new run-status value. Rejected admission creates no worker and does not turn unrelated execution into a failure. Results and counts identify added work explicitly; the guest is never presented as having awaited it.

## Acceptance

Write failing public-boundary tests before feature code. Extend existing controller/control/CLI/process owners for duplicate/lost receipts, conflicting request IDs, wrong session/generation, task/file limits, exhausted capacity, append versus completion/Pause/Stop, interleaved guest/addition replay, crash after dispatch intent, unknown cleanup, original-source drift and exact capability ceilings. Added workers must appear in status/watch/graph coverage and retain their results/captures. A terminal event follows all owned cleanup, never merely guest completion.

Use fixture-process tests for deterministic failure races, then a limited native read-only acceptance that proves an added worker uses the existing pinned backend without API-key billing. Review retained effects and positive cleanup; do not repeat an uncertain probe. Finish combined tests/check/smoke and a fresh independent review. No Actions enable/dispatch, release, cache replacement or installation is authorized by this design.
