## Live observation after every detached start

Use `watch "<run-id>" --session "<originating-session>" --generation N --after 0 --jsonl` with the same explicit data directory. This read-only command uses the run's recorded runtime and exits on its durable run-terminal event. `--poll-ms` is 100–10,000 (default 500); `--idle-ms` is 1,000–86,400,000 (default 60,000). Idle warnings mean no newly observed completed command/file-change activity for a running worker. Commentary does not reset the clock; a warning is not proof of deadlock or permission to restart.

Name an attached coordinator or collaboration observer for each detached run, resume and restart. Give it the exact watch argument array, run/generation, and originating coordinator identity. It consumes JSONL continuously, saves the last processed durable event `seq`, and promptly sends worker failures/unknown outcomes, idle warnings and run terminal to that coordinator through the available collaboration channel. A spawned observer without a consumed `attached` record is not confirmed. The CLI does not push into the host chat or modify a parent thread; the attached observer supplies that bridge. If no collaboration observer is available, the coordinator must keep the watch attached itself.

After a dropped consumer, reconcile saved status and reconnect with `--after` set to the last event the consumer actually processed. Retain the same session and exact generation; a new generation requires fresh attachment. Do not advance a cursor from unprocessed output. Watcher exit, EPIPE, or an idle warning never stops, retries or cancels workers. An observation error means monitoring coverage is missing; report it and inspect the retained run. Older retained runtimes may not support watch. Inspect their existing status/result explicitly and disclose the missing live surface instead of silently migrating them.

When shared-desktop compatibility has been explicitly authorized for this Windows Session 0 context, follow [Session 0 compatibility](../workflow-setup/references/session0-compatibility.md) and add --session0-desktop shared to each new run. Saved runs inherit their original selection on resume/restart. Inspect applied evidence separately from the request; preserve failures without automatic retry.

All commands accept --data-dir for explicitly selected state; keep it consistent. Otherwise use AGENT_WORKFLOW_DATA_DIR if set, then LOCALAPPDATA/agent-workflow (home .local/share/agent-workflow if LOCALAPPDATA is absent). PLUGIN_DATA does not implicitly select another instance. If installation is missing or changed, use workflow-setup.

Runs normally continue until script completion or manual Stop, and the dashboard stays available until explicitly closed. Do not infer that the host session ending stops either process. This version defaults workers to unbounded wall time; `run`/`resume --worker-timeout-ms` accepts a positive safe integer for an explicit budget, or 0 to remove it. A task's `timeoutMs:null` overrides a finite run default. For a deliberate overall wall limit use `--run-timeout-ms` (1–86,400,000; 0 removes it). Resume inherits saved limits unless overridden. Startup, individual command, interruption, cleanup, CPU/memory and no-broker-work idle protections remain separate. Older retained runtimes may have finite defaults; check the recorded runtime before authoring controls.

For independent work added to an active run, follow [live append](../../docs/live-append.md): preallocate a request UUID, supply a bounded task file and inspect that same receipt after any lost response. Additions use the original captured inputs, capability ceiling and shared scheduler. They cannot grant new skills/tools or dependencies. Use [worker deadline control](../../docs/worker-session-control.md) to set, extend or clear an active budget with exact generation/position/attempt/turn/revision. Neither operation authorizes automatic repetition of uncertain effects. Older retained runtimes may support neither operation.

Workers use pinned native Codex App Server with existing managed ChatGPT login. There is no API-key fallback, custom MCP server, parent conversation clone, native composer switch or shared parent token budget. Parent execution authority comes from the captured host context; native catalog provisioning does not manufacture parent-host connector or browser sessions. Report unavailable integrations explicitly. Observed usage is evidence, not a hard spending cap. Workflow mode alone grants no permissions. Windows Session 0 compatibility is explicit; see docs/verification.md for tested SSH scope and remaining limits.
