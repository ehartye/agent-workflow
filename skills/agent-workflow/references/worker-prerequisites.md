# Worker prerequisites

The coordinator prepares the toolchain and reviews artifacts; admitted workers perform the task's authorized operations. Workers use isolated worktrees and restricted launch environments. Parent-session tools, dependencies, caches and grants are not inherited authority. Read [worker capabilities](../../../docs/worker-capabilities.md) for the implemented immutable bundle and native skill-tool mechanism. Exact `selectedCapabilityRoots` bindings expose executor `skills.list`/`skills.read`; workers invoke returned packages. Manual file reads, copied prompt bodies and CLI discovery cannot substitute. [Native acceptance](../../../docs/verification.md) distinguishes verified invocation/managed authoring from unverified rendering and artifact objectives.

Select only bundle-declared skill/tool IDs through the integrated public API. Required tool readiness must pass inside the actual restricted worker before tool-dependent inference. Selecting a skill without requiring its tool permits independent source authoring, with unavailable/unverified tool stages reported. Optional operations still need their own readiness and task authorization before execution. Never turn a missing required tool into an optional one to bypass admission.

Record four separate prerequisite observations in the actual restricted environment:

1. **Executable discovery:** the coordinator-verified absolute executable and package/cache paths are present. Host discovery or a version string alone does not prove worker execution.
2. **Command admission:** a bounded invocation is permitted and its process-start/exit evidence is observed. Keep command-startup, pipe and ACL failures distinct from missing packages or cache entries.
3. **Browser installation:** the required browser package and browser binaries exist in the selected cache. This does not establish command admission or rendering.
4. **Sandbox render transport:** the intended browser integration can launch, communicate with and paint a page in this environment. An installed browser or passing host render does not prove this stage.

Tool identity includes the exact Node executable and managed launcher, installed runtime/source/dependency receipts, original plugin paths and explicitly selected managed-home/cache values. Keep skill references and assets in their original plugin-relative layout. A cache launcher, installed runtime and browser cache are distinct inputs; presence alone does not verify their identities or usability. Bounded readiness commands are nonmutating; version/capability output cannot prove a build, render, loopback transport or generated artifact.

Do not automatically install prerequisites, change PowerShell execution policy, or expand filesystem/network permissions to make a command work. A missing validation prerequisite pauses only dependent checks; independent authorized source authoring/review continues. See the [friction evidence ledger](../../../docs/friction-delivery.md) for observed cases and remaining verification. Keep earlier failed/unknown observations even when later coordinator setup succeeds.

Use bounded reads/commands, coordinator-verified executables and separate arguments. Disable PowerShell profile loading with `-NoProfile` where supported; use `-NonInteractive` for unattended commands. For retained UTF-8 text use explicit `Get-Content -Encoding UTF8 -TotalCount <bound>` and narrow `rg` searches. Profile loading, executable selection, quoting, text decoding and sandbox startup are separate observations; do not infer a common cause from an exit code or garbled report text.

On Windows, an `npm` command may resolve to an execution-policy-blocked `npm.ps1`. Supply the verified `npm.cmd` executable when needed. MXC redirects `LOCALAPPDATA`, which can move implicit npm and Playwright cache lookups. The coordinator owns explicitly authorized dependency/browser preparation and supplies verified paths; missing cache entries do not authorize downloads or alternate versions. Once actual worker readiness passes, workers may perform authorized builds/exports and capture outputs in their assigned roots. If readiness is missing, continue independent authoring and list the unrun operations.

Before authorizing installation/build inside a writer worktree, account for artifact capture: by default all untracked outputs are included even when ignored, including `node_modules` and `dist`. The current limits are 20,000 files, 128 MiB captured bytes and 32 MiB per diff. A successful installation can therefore prevent final diff capture. Prefer coordinator-side dependency installation/build when it would exceed these limits. Alternatively a new run may receive an explicit coordinator-owned [immutable capture policy](../../../docs/session-delivery.md#explicit-writer-capture-policy) before dispatch, protecting every assigned output and retaining an excluded metadata inventory. Worker-edited ignores never set capture authority. Capture failure preserves the workspace and unknown status; inspect `workspaceError.capture` for its stage and sanitized cause. Do not delete evidence, retroactively change policy or replay an unknown writer to obtain a cleaner result.

For preinstalled Playwright browsers, the launch path explicitly forwards `PLAYWRIGHT_BROWSERS_PATH` and includes it in backend identity. Keep it consistent on resume and dashboard launch. The public bundle additionally validates declared `AGENT_BEEPS_HOME` and `AGENT_SPRITES_HOME`; conflicting values reject. Passed required tools provide exact Node/launcher and named environment metadata to the initial task. Optional tools remain unverified. Do not assume arbitrary parent environment is forwarded or invent host-selected roots. A browser cache does not prove rendering transport; none of these values grants installation or broader permissions.

Readiness commands and task/correction turns share the worker deadline beginning immediately before readiness, after existing App Server/thread startup. Each stage and RPC is capped by remaining time; no further command/turn starts after expiry. Cleanup has its separate drain budget. Plan required tool stages within the shared budget, not as extra time before it.

Preserve every declared skill resource at its original path and hash all files exposed beneath the selected root. After genuine native activation, a linked ordinary document outside native package scope may be read through a bounded command only when its exact path/hash was explicitly declared and verified. Never treat this as permission to read `SKILL.md` manually or activate another skill. A known read-only syntax/compatibility failure may receive a narrow correction once its effects and input contract are understood; unknown or potentially mutating effects still require coordinator reconciliation, with no implicit fallback or retry.

After a startup or preflight failure, report the exact command and arguments, working directory, executable/package/cache paths, failing prerequisite stage, observed process-start evidence and exit code (or explicitly unknown), bounded sanitized output/evidence reference, and remaining dependent checks. A process that ran and exited nonzero is not `notStarted`; it may already have changed files. Use `notStarted` only when tool evidence explicitly confirms no process began. Unknown or potentially mutating effects require coordinator reconciliation before retry/fallback. Report unrun checks and incomplete assets explicitly in the final result.

Retain selected IDs/fingerprints, exact native root bindings, executor list/read observations and returned `skill_root`, associated tool readiness and missing stages. Native source support is separate from observed invocation and artifact production. Report command start/exit/marker/cleanup facts without raw secrets/configuration dumps. Capture required PNG/atlas/WAV/measurement/config outputs under assigned writer roots for integrity review; a tool status or worker claim cannot certify their effects or acceptance. Root owns actual render/listening acceptance and independent integration verification.

## Browser ownership and phone acceptance

Name one browser verification owner before checks begin. The coordinator/designated verifier retains the exact integration and tab/context, source/build identity, target URL, required states and pending checks. Hand off that information explicitly when ownership changes, and record who releases or retains the browser afterward. On a shared-lock/busy response, report the blocked check, instance/context, observed lock evidence, known owner (or unknown) and needed handoff; pause the browser check and continue independent work. Serialize shared use. Separate contexts are appropriate only when that integration supports verified isolation; do not bypass its lock. Busy is a verification blocker, not evidence of product failure.

For rendered acceptance, wait for fonts and assets to settle, then inspect actual painted glyphs at the required viewport, device pixel ratio, theme and product states. Record readable text and clipping/overlap evidence. For a phone learning game such as Tidepool, this includes clear numbers and the problem **and** custom keypad visible simultaneously. DOM labels, nominal font sizes, button/hitbox bounds, lack of overflow and successful taps alone do not establish readability. The coordinator owns game rendering acceptance; a dashboard layout report is not a game glyph receipt.
