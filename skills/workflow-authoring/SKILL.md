Before drafting a script, record the input decision: inline JSON, a snapshotted `--args-file`, or frozen manifest/chunk batching. Read [large inputs and bounded batches](references/large-inputs-and-batches.md) for the required size, freshness and call-budget checks. Version 0.3.6 supports `--args-file`; earlier installed 0.3.5 requires an explicit update. A file avoids command-line limits; it does not expand the evaluator or worker prompt limits. Keep the per-role genuine skill/tool selection below even when inputs are file-backed.

Record the corresponding output decision in the same plan: small schema result or owned captured artifacts plus a bounded summary. The [output handoff section](references/large-inputs-and-batches.md#output-handoffs) distinguishes transport headroom, retained previews, answer and artifact limits; larger file capture is not a larger conversational response allowance.

Before drafting launch or recovery commands, read [worker admission and replay](references/worker-admission-and-replay.md) and [complete-plan acceptance](references/complete-plan-acceptance.md) through the genuine native package. Deliver the complete owned plan artifact, then return a small path/hash/byte-count summary. Include per-role skill/tool choices, reviewed capture/integration, fresh verification, observer ownership and both recovery cases. An empty `missing[]` is not semantic acceptance.

Use the actual callable shapes: `parallel(items.map(item => () => agent("Read " + item.id)))` takes thunks, not `parallel(items, callback)`. A `project:` definition belongs to its save checkout; verification in a different combined checkout needs an absolute, verified `--script` file or an explicitly saved definition there. Complete the path from genuine effect reconciliation through replacement/integration/fresh verification in the artifact; preserve historical unknown evidence without turning its mere presence into a permanent block after authorized recovery. Unsupported commands and an unwritten future plan fail acceptance.

Required package loss and changed catalogs are blocked recovery cases. Preserve the old result/effects and completed writers. Reconcile effects, verify current resources and use a fresh admitted run; never rewrite saved context/bindings or substitute a package to make resume pass. Explicit selected skills require their original initial native main read; source hashes are checked again after the model. Check required/observed/missing IDs rather than paired-call counts or worker claims.

Author a saved script using the existing separate QuickJS evaluator. Read [the runtime API](../agent-workflow/references/runtime-api.md) and use [the main skill](../agent-workflow/SKILL.md) for validation, saving, starting and inspection. Use existing CLI/native-worker surfaces; no planner service, custom MCP or host evaluation is needed. The immutable capability bundle and `agent` skill/tool selections are implemented. [Verification](../../docs/verification.md) records accepted native invocation/nonrendering authoring separately from unverified rendering/export.

Use the bundled [decomposition-delivery recipe](../../workflows/decomposition-delivery.js) when a fixed worklist needs actual deliverables after scouting. Read [the recipe contract](references/delivery-contract.md) for arguments, bounded result schemas and the coordinator acceptance gate. It has two explicit invocations: `deliver`, then `verify` from a coordinator-prepared integrated checkout. It never integrates files or decides to replan itself.

## Scope before dispatch

New starts default to parent access. Capture the **current originating session's** actual permission context in an owned JSON file and pass `--parent-access <file>`; the owner should not have to author that file or individual executable grants. Use the six-field snapshot in [the access contract](../../docs/superpowers/specs/2026-10-14-parent-worker-access.md#policy-admission). Do not infer it from a new child server, hardcode full access for another parent, or silently reuse an outdated context. Missing or unsupported authority stops admission. Use `--access restricted` when restricted execution is intended. Saved runs retain their original recorded authority.

Parent mode inventories the enabled native catalog and binds original plugin and standalone skill roots. Installed resources do not prove application startup, and native connections do not prove every parent-host connector is available. Preserve missing inventory and native warnings. Full-access writers use `workspace:'isolated'` for owned edits and captures; those worktrees organize changes and do not impose filesystem security isolation. An explicit `permissions` override really narrows execution and may prevent application startup.

Finish temp-producing tests and freeze a stable source checkout before isolated input capture; concurrent fixture creation/removal can invalidate a capture. Canonical external systems such as the wiki vault need their own guarded operation and path ownership, not a project patch capture. Put that work in a separate parent-access run with an explicit external write scope; omit the run-wide `--writable` default that would otherwise select an isolated project workspace. This does not widen captured parent authority or waive that system's operation/commit checks. After admission failure, inspect the actual worker's `notStarted`/`noProcessStarted`/`noInference` and cleanup facts before authoring any replacement; a generic notification category alone is insufficient.

Keep live coordinator receipts, observer logs, gate files and dashboard outputs **outside the captured source checkout**, including its excluded directories. Capture compares excluded metadata across passes; an appended log or atomic receipt replacement can invalidate it. Exclusion skips payload capture, not enumeration. Record absolute source/control paths separately and verify the source is stable before the first writer. Inspect a failed input capture's persisted stage and cause; never recollect an old capture or retry uncertain effects.

Before saving or starting, check every public CLI flag against the installed help/API contract. `run --concurrency` limits simultaneous workers; `--max-agents` is not a supported CLI flag. Bound total requests with a fixed script worklist, bounded loops/revisions and explicit per-worker `maxAttempts`; concurrency alone does not cap total work.

Retain the user's requested outcomes as objective IDs. Inventory enough real paths and prerequisites to choose a useful split. Give each task a stable ID, objective IDs, full phase label, inputs, exclusions, read scope, write ownership, prerequisites, dependency IDs, artifact contract, acceptance checks and an explicit deadline policy. An orchestrator-controlled session without a wall deadline is valid; do not impose an arbitrary expiry. Check the installed runtime's actual limits before promising live changes. Save this `PlanRevisionV1` in script arguments. Default to at most 32 tasks and two explicitly authored revision rounds; decide overrides before dispatch.

Shared interfaces, lockfiles and integration files each have one named writer. Several workers may read the same source; writers must have disjoint literal paths or directory prefixes, including case collisions on Windows. Reading a path is not permission to edit it. Reject overlapping ownership before dispatch. Do not assign the entire repository to every worker. The recipe refuses unsafe paths, forward dependencies and ownership overlaps.

Choose the shape that matches the work: independent readers can run in parallel; item-local transformation/checks can use `pipeline`; dependent calls need recorded `dependsOn` IDs; combined artifact integration needs a real barrier and coordinator review. A phase groups workers visually and conveys no dependency. Avoid splitting a change that requires simultaneous edits to the same interface.

## Select skills before workers start

Match skill procedure to role: do not assign a write-producing authoring skill to a source-only scout. Narrow source readers explicitly with `permissions:{sandbox:'read-only',networkAccess:false,approvalPolicy:'never'}` when their admitted operations support it. A prompt saying “read-only” does not enforce that boundary. An application that cannot run under the narrowed policy is a reported prerequisite gap, not permission to widen the role silently.

Skill selection is a required authoring decision for every scout, writer and verifier. Before launching the run, identify the actual plugin skills each role needs and record `worker ID → skills to activate → required tools` in its plan. Explicitly record none required for ordinary tasks. Parent mode makes the discovered enabled native catalog available; each role must still activate the skills it needs through genuine executor `skills.list` and `skills.read`, resolving duplicate names by the returned package and original root. Discovery is not skill use. Parent-host connections that the independent native server cannot expose remain missing.

When the owner requests a full modeling plugin, inventory its complete installed skill set and the associated managed tools before startup. Map the requested authoring, build/verify, rigging and preview operations to modeling roles, including required Blender support; do not silently reduce the request to one authoring skill or file access. Record runtime, dependency and cache prerequisites using [worker prerequisites](../agent-workflow/references/worker-prerequisites.md). Full plugin coverage still respects each stage's task and permission ceiling.

Read [worker capabilities](../../docs/worker-capabilities.md). Parent provisioning does not require hand-written per-file manifests. For an explicitly bounded role or required readiness gate, the original immutable bundle remains supported: declare source/resource/tool identities and pass its IDs through applicable `agent` calls' `skills` and `requireTools`. For example, when those IDs exist: `agent(prompt, {id:'buddies', workspace:'isolated', skills:['sprite-editing'], requireTools:['sprites-managed']})`. Restricted mode uses explicit declarations. Do not add fields to a strict recipe schema that does not forward them; author supported custom calls when necessary.

Preserve permission ceilings and admit required tool readiness in the actual worker environment before task execution. Exact `selectedCapabilityRoots` bindings expose genuine executor `skills.list`/`skills.read`; workers must invoke those actual tools with returned package/resource identities. Reading `SKILL.md` manually, copying its body, CLI discovery, or the parent's activation cannot substitute. Required admitted tools expose verified invocation metadata. Native calls, tool operations and artifact acceptance remain separate checks; rendering/listening/export gaps stay explicit. Baseline skills remain visible without blanket host grants.

Select before startup: the pinned native runtime cannot grant a missing skill root to an already-running worker. Steering does not change that selection. An unexpected out-of-bundle prerequisite requires a coordinator-reviewed plan for unfinished work, preserving original outcomes and effects; do not silently extend the bundle or restart an active worker.

Main-response evidence does not certify all pagination or instruction compliance. Source guards detect persistent drift; they do not prevent host cache deletion.

## Scouts lead to deliverables

Scouts perform read-only tasks. Parent execution access is broader than that task scope; do not describe it as a read-only filesystem sandbox. Require bounded file/scope inventories, proposed independent slices, shared-interface ownership, prerequisite observations and uncertainties. Pass that JSON into the deliverable worker's prompt. Use file references instead of bulky source dumps. Scout suggestions cannot widen the fixed scope or invent more workers; changed scope requires a reviewed revision.

For evidence-led improvements, use bounded retained status/activity/diff pages within the assigned read scope. Record source/version, exact run/report identity and observed generation/position/attempt where available; retain cursors, truncation and missing evidence rather than reconstructing omitted history. Classify findings as shipped, open or superseded against the current architecture, and assign each regression to its existing invariant/test owner. The [friction ledger](../../docs/friction-delivery.md) gives examples and falsifiable acceptance; supplied JSON and reference strings remain context claims, not proof of files or authenticated receipts.

Separate prerequisites for source authoring from prerequisites for validation. Inspect tools in the actual isolated worker environment, using coordinator-verified executable/cache paths. Read [worker prerequisites](../agent-workflow/references/worker-prerequisites.md). Missing build, rendering or browser tools block those commands while useful authorized source work continues. Missing an authoring prerequisite blocks that task. A lost scout leaves a null task slot; it is not an empty successful inventory.

Return the exact blocked command, executable/cache path and observed evidence. A process that launched and exited nonzero may have mutated files. Call it `notStarted` only with explicit evidence that no process began. Do not automatically install dependencies, change execution policy or permissions, or try an alternate mutating command after an uncertain effect. The coordinator prepares the toolchain and decides any authorized installation. Required tool readiness gates tool-dependent inference; optional unavailable tools leave dependent operations unrun while independent authoring continues. Admitted workers perform actual authorized tool operations and retain required generated outputs; deferring every asset operation to the coordinator does not deliver the worker skill/tool requirement. Source support for native list/read does not certify Windows invocation or plugin artifact production.

## Early artifact checkpoints and live ownership

Give each writer an early minimal artifact checkpoint before polish: create the smallest useful owned source/artifact and run its first applicable check, then refine it. Record the checkpoint and its evidence in the task inputs/acceptance plan using existing fields; do not invent recipe schema fields. A long stream of analysis or commentary is not an artifact checkpoint. An observed file change still requires retained-capture integrity and coordinator review before acceptance.

The coordinator starts the workflow under its actual originating session. Name a live observer before every detached launch, resume and restart, and arrange immediate receipt delivery rather than doing other work before attachment. A collaboration observer attaches using the exact read-only `receipt.watch.argv`; carrying that session identity for observation does not authorize impersonating the parent to launch or control work. Follow [live observation](../agent-workflow/SKILL.md#live-observation-after-every-detached-start): confirm attachment, retain processed durable cursors, and relay failure/unknown, idle and terminal events promptly to the originating coordinator. Missing observation must be reconciled explicitly. Neither dashboard visibility nor a startup receipt proves that somebody is watching. A warning triggers bounded inspection and a report, not an uncertain-effect retry or cancellation.

## Review, integrate, verify

Dependency completion orders calls. It does **not** transfer predecessor edits between isolated worktrees. JSON reports are context and artifact claims. A writer that needs predecessor bytes must stop that dependent portion and report it incomplete until a coordinator supplies a new verified snapshot. Do not reconstruct, copy or apply predecessor patches from prompt claims.

For each handoff, the coordinator records the producer run, generation, position and observed cumulative attempt, authoritative capture reference and hashes, allowed paths, and reviewed acceptance evidence. Resolve those identities from saved records rather than guessing dispatch positions. The evaluator does not expose them to scripts, so recipe `workerRef` fields stay null until the coordinator resolves them externally.

The coordinator checks verified drain, original outcome/effect reconciliation, manifest/blob integrity, source ownership and complete output scope before using retained artifacts. Review partial and binary artifacts too. A hash confirms bytes; it does not prove that an objective is satisfied. Worker ignores, prose, `delivered`, or a `passed` Boolean cannot supply authoritative capture or acceptance evidence.

After reviewed integration, prepare a dedicated checkout of the combined source and record its content identity. Start a **new** `verify` run there with the originating session and data instance, recording its selected runtime identity. Supply the reviewed producer handoffs and integration/snapshot references. Read-only workers inspect the launch checkout; the runtime does not create an isolated writer capture for them. Keep that checkout stable during verification and recheck its content identity before accepting results. Verification workers inspect actual files and run admitted checks within their task/permission scope. Assign authorized build/export operations to suitable writers with verified readiness; services/shared sessions require separate authorization and ownership. Root owns independent combined verification and actual render/listening acceptance; absent prerequisites remain reported gaps. Cached replay results cannot establish freshness.

Use the [coordinator handoff checklist](references/delivery-contract.md#coordinator-handoff-checklist) beside the integration example. It records reviewed captures/allowed paths, stable snapshot identity, one browser owner with explicit handoff, and pending checks in separate coordinator evidence. For an exact persistent dashboard instance, name who retains it through verification and who uses Close afterward; retain shutdown evidence. Closing a tab or ending the host conversation does not prove shutdown. Close ends the dashboard; Stop controls workflow execution.

The recipe records supplied references as claims; it cannot authenticate them. It reports fresh checks as `reported` or `unverified`, never `accepted`. Its `complete` stays false and all unaccepted objective IDs remain missing. For the final user-facing completion decision, the coordinator must independently accept every retained objective, resolve captures and check receipts, finish integration, and pass all required fresh checks. Retain the recipe output unchanged and keep the authoritative acceptance report separate. Missing or null verifier slots, missing artifacts, failed checks and incomplete integration cannot be filled by synthesis or worker count.

## Revise explicitly

A revision appends replacement links for unfinished scope, names the prior run and exact generation/position/attempt, and preserves prior failed/unknown outcomes, usage, effects, artifacts and controls. Do not overwrite old execution evidence or silently drop objective IDs. Explicitly describe a user-authorized objective change rather than treating it as delivered.

This guest has no trusted receipt resolver. An uncertain-effect or unknown-outcome replacement is **coordinator-required and never dispatched**, even if JSON arguments contain nonempty reconciliation/drain references or label effects `reconciled`. Independent safe tasks can still proceed; dependencies of the blocked task retain null coverage. Native restart/recovery admission must be performed through the existing authenticated runtime outside this recipe. A revision, new task ID or new run is not a way to bypass that admission. Do not autonomously retry or replan after a failed or unknown worker.

Native restart repeats the selected worker **and every later worker**, including completed writers. Review the entire suffix and its effects before authenticated admission. Clean job drain alone, claimed reconciliation or successful later delivery cannot authorize uncertain repetition or rewrite historical outcomes.

When reporting progress, distinguish execution status, declared task outcome, artifact integrity, integration and accepted verification. A schema-valid blocked report can come from an engine-completed worker. Report all missing objective IDs, null reports, blocked commands and required coordinator actions explicitly.
